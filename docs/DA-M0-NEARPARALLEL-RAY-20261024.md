# M0 finite convex ray: near-parallel is not the same as exactly parallel

Original `intersectNormalized` treated `abs(dot(unit normal,unit ray)) <= angleTolerance` as exact parallelism. When the source lay sufficiently outside that face, it immediately returned `miss` and could promote a whole supplied-scene `clear` verdict. This inference is invalid for any nonzero ray slope: at an arbitrarily large positive t, the ray may enter that face. In particular, finite binary64 dot cancellation can round a mathematically nonzero nearparallel slope to exactly 0. This is a reusable public M0 ray bug independent of the solid kind, question, plane position or observer view.

Now consume the already-merged **opt-in exact sign evidence** `certifyDotSign` from #629 ONLY within the existing nearparallel branch. When represented-binary64 sign is nonzero, the face adds ambiguity, and no certified miss is inferred from assumed parallelism; a truly zero exact slope retains the prior proof of an outside parallel-plane miss. No new tolerance, solver, V5, ConstructionIntent or ray trace engine is introduced. Actual nearparallel finite depth may still be resolvable with an independent bounded ray range; until then, keep `undetermined` (conservative). All other real hit branches and first-angle observer settings remain as before.

Independent regression: construct two normalized 3D directions whose rounded dot is exactly zero while the shared dyadic sign is strictly negative; outside supporting plane must NOT yield a false miss/scene-clear. A mathematically true parallel control retains the miss, ordinary exact box ray maintains entry and exit 2/4 mm. Final style and whole scene are never certified by a point ray.
